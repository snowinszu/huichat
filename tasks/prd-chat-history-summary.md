# PRD: 聊天历史摘要与截断

## 1. Introduction/Overview

聊天记录会随着使用时间越来越长。目前应用在给 AI 生成回复、润色、评估目标时，都会把这段对话**从头到尾全部**塞进提示词（prompt）里——聊得越久，这段文字就越长，最终会导致：AI 服务收费变贵、响应变慢，甚至超出模型能处理的上下文长度上限而直接报错。

本功能的做法是：一旦一段对话超过"最近 100 条"这个安全窗口，就把窗口之外、更早的那些消息用 AI 压缩成一段简短摘要保存起来，之后再需要用到这段更早的历史时，只带上"摘要 + 最近 100 条原文"，而不是全部原文。这样即使聊了几千条消息，实际发给 AI 的内容量也能保持在一个可控范围内，同时又不会真的把很久以前聊过的内容彻底遗忘。

（说明：本次讨论中提到的"每 20 条对话提取一次对方信息补充到对方基本信息"这一需求已经在此前的会话中实现并验证完毕，不属于本 PRD 范围，本 PRD 只处理"历史摘要与截断"这一块。）

## 2. Goals

- 当聊天记录超过 100 条消息时，自动把更早的历史压缩成一份摘要，持久化保存。
- 摘要随对话继续增长而滚动更新（合并进新的更早消息），而不是无限累积多份摘要。
- 生成回复、润色、目标评估三个用到完整聊天历史的功能，在历史超长时自动改用"摘要 + 最近 100 条原文"，无需用户任何操作。
- 历史未超过 100 条时，现有行为完全不变。
- 摘要生成失败或耗时，绝不能影响用户当前正在使用的功能（发消息、生成回复等）。

## 3. User Stories

### US-001: chat_card 新增摘要相关字段
**Description:** As a developer, 我需要在 `chat_card` 表中新增字段来保存滚动摘要文本和"已摘要至哪条消息"的水位线，以便后续摘要逻辑能持久化状态。

**Acceptance Criteria:**
- [ ] `chat_card` 表新增 `history_summary`（TEXT，默认空字符串）和 `summarized_through_message_id`（INTEGER，可为 NULL，默认 NULL）两列
- [ ] 为已存在的数据库提供迁移（`ALTER TABLE ... ADD COLUMN`），确保历史安装的 app.db 升级后不会因为"表已存在、缺列"而报错（参考本项目此前 `debug_prompt_export` 字段踩过的同类坑，迁移逻辑放在 `electron/main/db/migrations.ts`）
- [ ] `ChatCardRecord` 类型新增 `historySummary: string` 和 `summarizedThroughMessageId: number | null`
- [ ] `chatCardRepository.ts` 的读写方法正确处理这两个新字段，其余现有字段行为不受影响
- [ ] Typecheck/lint 通过

### US-002: Token 数量启发式估算函数
**Description:** As a developer, 我需要一个不依赖第三方分词库、纯本地计算的 token 数量估算函数，用来判断"待摘要的老消息内容"是否已经多到需要触发摘要。

**Acceptance Criteria:**
- [ ] 新增 `estimateTokenCount(text: string): number` 纯函数，基于字符数做启发式换算（不引入新的 npm 依赖）
- [ ] 对中/日/英混合文本给出的估算值处于合理量级（不要求和真实 tokenizer 完全一致，只要求单调、稳定，能用于阈值比较）
- [ ] 空字符串返回 0
- [ ] Typecheck/lint 通过

### US-003: 历史摘要生成与滚动更新
**Description:** As a user, 我希望在聊天记录变得很长时，系统能自动把很久以前的对话压缩成摘要保存下来，这样后续对话依然能"记得"更早发生过的事情，而不需要每次都把全部原文发给 AI。

**Acceptance Criteria:**
- [ ] 新增函数（如 `maybeSummarizeHistory(db, chatCardId)`），在每次消息插入后被调用（fire-and-forget，不阻塞插入），语义与已有的 `maybeExtractInfo` 一致
- [ ] 仅当"保留窗口（最近 100 条）之外、且尚未被摘要覆盖"的消息内容估算 token 数达到阈值时，才真正触发一次摘要生成；未达到阈值时函数直接返回，不产生任何 LLM 调用
- [ ] 触发时，调用 LLM 把"已有摘要（如果有）+ 这批新的老消息内容"合并压缩成一份新的摘要文本，写回 `history_summary`，并把 `summarized_through_message_id` 推进到这批老消息中最新一条的 id，确保同一批消息不会被重复摘要
- [ ] 生成的摘要文本本身有长度上限（如不超过 500 字），避免摘要随对话不断进行而无限膨胀
- [ ] 摘要生成失败（无当前模型、网络错误、响应异常等）时静默失败并记录日志，不能抛出未处理异常，不能阻塞消息插入或其他功能
- [ ] 该次 LLM 调用复用现有的调试导出机制，来源标注为"历史摘要"
- [ ] Typecheck/lint 通过

### US-004: 生成回复/润色/目标评估接入摘要与截断
**Description:** As a user, 我希望在对话很长的情况下，点击"生成回复"（或"润色"、查看目标评估）时，AI 依然能给出贴合上下文的结果，而不是因为历史太长而变慢、出错，或者要我自己等一次专门的"摘要"操作。

**Acceptance Criteria:**
- [ ] 修改共用的历史上下文构建逻辑（`buildContextSection`）：当聊天记录总数超过 100 条时，改为使用"已保存的历史摘要 + 最近 100 条消息原文"构建提示词里的聊天记录部分，而不是全部历史原文
- [ ] 聊天记录总数不超过 100 条时，行为与现状完全一致（无摘要、无截断，直接使用全部原文）
- [ ] 因为"生成回复""润色""目标评估"三个功能共用这同一段上下文构建逻辑，接入一次即可让三者同时生效，无需分别修改
- [ ] 当前还没有任何已保存摘要、但历史已超过 100 条时（摘要尚未来得及生成），使用"最近 100 条原文"且不包含摘要占位内容，不报错
- [ ] Typecheck/lint 通过

### US-005: 端到端测试——历史摘要与截断完整流程
**Description:** As a QA engineer, 我想要一个自动化端到端测试覆盖"消息积累到阈值 → 自动生成并保存摘要 → 后续生成回复实际使用摘要+最近原文而非全部历史"的完整链路，防止未来改动引入回归。

**Acceptance Criteria:**
- [ ] 自动化 E2E 测试（Electron + mock LLM server）为一个聊天卡片插入足够多消息，使其同时超过 100 条保留窗口和摘要触发的 token 阈值，断言 `chat_card.history_summary` 被写入非空内容、`summarized_through_message_id` 被正确推进
- [ ] 断言摘要生成之后触发的"生成回复"，其实际发送给 LLM 的 prompt 中包含摘要文本，且不包含已被摘要覆盖、超出最近 100 条范围的最老消息原文，但包含最近 100 条窗口内的消息原文
- [ ] 覆盖边界路径：消息数量虽然超过 100 条、但还不足以让"待摘要内容"达到 token 阈值时，断言不会产生摘要（`history_summary` 仍为空），且此时生成回复用的仍是全部历史原文
- [ ] 覆盖边界路径：摘要生成对应的 LLM 调用失败时，断言不影响"生成回复"功能本身依然正常返回候选回复
- [ ] 测试在 CI 中可运行并通过
- [ ] 测试自行创建并清理所需的聊天卡片和消息数据，不依赖测试执行顺序

## 4. Functional Requirements

- FR-1: 系统必须为 `chat_card` 新增 `history_summary` 和 `summarized_through_message_id` 字段，并为已有数据库提供迁移。
- FR-2: 系统必须提供一个基于字符数的启发式 token 数量估算函数，不引入第三方分词依赖。
- FR-3: 系统必须在聊天记录总数超过 100 条时，判断"保留窗口之外、尚未被摘要覆盖"的消息估算 token 数是否达到阈值。
- FR-4: 当达到阈值时，系统必须调用 LLM 把已有摘要与新的老消息内容合并压缩成一份新摘要，并持久化保存。
- FR-5: 系统必须在每次生成新摘要后推进"已摘要至"水位线，避免同一批老消息被重复摘要。
- FR-6: 系统必须限制生成的摘要文本长度上限，避免摘要无限膨胀。
- FR-7: 系统必须在聊天记录总数超过 100 条时，把"生成回复""润色""目标评估"三个功能使用的历史上下文替换为"已存摘要 + 最近 100 条消息原文"。
- FR-8: 系统必须保证聊天记录总数未超过 100 条时，历史上下文构建行为与现状完全一致。
- FR-9: 摘要生成失败时，系统必须静默失败并记录日志，不能阻塞消息插入或任何其他功能。
- FR-10: 摘要生成对应的 LLM 调用必须复用现有的调试导出机制，来源标注为"历史摘要"。

## 5. Non-Goals (Out of Scope)

- 不提供任何 UI 供用户查看、编辑或手动触发历史摘要。
- 不提供关闭本功能的偏好开关——只要历史超过阈值，摘要机制始终生效，没有开关可以让用户回退到"始终发送全部历史"。
- 不引入专门的 tokenizer 库；token 数为启发式估算，不追求与真实 tokenizer 完全一致。
- 不改变"自动信息提取"功能的现有行为——它本身只处理最近一批（20 条）消息，不存在历史无限增长的问题，因此不需要接入本功能。
- 不支持对已生成的摘要做人工编辑、回退或重新生成的入口。
- 不做多版本摘要历史管理，只维护一份不断合并覆盖的滚动摘要。
- 已被摘要覆盖的原始消息若之后被用户用"删除消息"功能删除，摘要内容不会跟着回退更新（摘要一旦生成即不可逆）。

## 6. Design Considerations

本功能完全是后台机制，不涉及任何新增 UI 界面或组件。

## 7. Technical Considerations

- 核心改动文件：
  - `electron/main/db/schema.ts`：`chat_card` 新增两列
  - `electron/main/db/migrations.ts`：新增列的迁移（`ALTER TABLE ... ADD COLUMN`），沿用最近为 `debug_prompt_export` 添加迁移时的同款模式
  - `electron/shared/ipc-types.ts`：`ChatCardRecord` / `UpdateChatCardInput` 扩展
  - `electron/main/db/chatCardRepository.ts`：读写新增列
  - 新增一个纯函数模块（如 `electron/main/llm/estimateTokens.ts`）：`estimateTokenCount`
  - 新增一个模块（如 `electron/main/llm/summarizeHistory.ts`）：`maybeSummarizeHistory` 及摘要用的 prompt 构建函数
  - `electron/main/llm/promptContext.ts` 的 `buildContextSection`：接入"超过 100 条则用摘要+最近 100 条"的逻辑
  - `electron/main/ipc/register.ts` 的 `messageInsert` handler：消息插入后以 fire-and-forget 方式调用 `maybeSummarizeHistory`，写法与现有 `maybeExtractInfo` 调用一致
- 保留窗口固定为 100 条消息，作为代码内常量，不做成用户可配置项。
- Token 估算使用简单字符数启发式（如 `Math.ceil(text.length / 1.5)`），不引入新依赖。
- 摘要触发阈值（"待摘要老消息"估算 token 数）默认取一个内部常量（建议 3000），供实现阶段按实际效果微调，不暴露给用户配置。
- 摘要生成属于额外的一次 LLM 调用，与已有的"自动信息提取"批量调用一样，都应遵循"fire-and-forget、失败静默、不阻塞主流程"的既有约定。

## 8. Success Metrics

- 聊天记录超过保留窗口后，实际发送给 LLM 的 prompt 体积不再随对话历史线性无限增长。
- 数百条消息量级的长对话下，"生成回复"等功能依然能正常返回结果，不因 prompt 过大导致模型上下文溢出报错。

## 9. Open Questions

- 摘要触发阈值（暂定估算 3000 token）和摘要长度上限（暂定 500 字）的具体数值需要在实现后根据真实使用效果微调，当前作为内部常量的初始假设值。
- 若聊天卡片关联的角色设定（persona）或对方基本信息在摘要生成之后发生较大变化，摘要内容不会自动重新生成或修正，只会随后续新一批老消息的合并而逐步"更新"到最新状态。
